# Inbox, search, read state, notifications and refresh (Android + browser prototype)

Branch `feature/mobile-inbox-final-polish`, from `feature/mobile-inbox-notifications` (`986d31b`), which came from `feature/android-offline-mesh` (`1a81af1`). The final polish pass is described in the last section. The app is still the Kotlin BLE engine with SQLite storage and the bundled WebView UI from `prototype/` (Gradle copies it into the APK; the UI is not forked). Nothing was migrated to Flutter. The desktop simulator and its routing engine are not touched.

The aim is **discoverability and continuity**: receive a request, notice it, dismiss it, find it later, respond.

## What changed

| | Behaviour |
|---|---|
| **Refresh** | A refresh button in the header (labelled "Check for new messages", 44 px). It re-reads this phone's own SQLite snapshot immediately, then asks the existing BLE transport to start/resume looking for nearby phones if the phone allows it. It shows a subtle busy state and then a completion line. It counts arrivals **from the database**, never from the radio call: "N new messages arrived" only if packets were really stored; otherwise "Nothing new has arrived. Messages only come from nearby phones that have Relay." Bluetooth off / permission missing / no BLE each get their own honest line ("Showing messages saved on this phone. ..."). Taps within 1.2 s do nothing extra. Tab, scroll, search text, filters and every unfinished draft are kept. In the browser prototype it re-draws the list and says so; it never advances the simulated clock or creates a packet. No wording mentions a server or the internet |
| **In-app pop-up (important messages only)** | A compact live-region pop-up between the header and the content (never over an input): "Medical assistance requested · Lodhi Colony" with **Open message** and **Dismiss**; the message text is tappable too. It appears **only for important messages** (next section); every other new message just appears in *New to you* and on the Inbox badge, so the app never nags. It never repeats for the same packet. **Two or more at once become ONE pop-up, "N new messages — tap to open and check them", that opens the inbox.** Dismissing leaves the message unread. Opening routes to the exact message while a half-written form stays as typed. About has **In-app pop-ups: Important only / Off** (remembered); Off never affects the inbox |
| **Android notifications (app in background or closed)** | Posted from the engine's own "newly stored, validated packet" signal. **One new message gets its own notification** (tapping it opens exactly that message, with its own PendingIntent: unique `relay://open/...` data URI + request code + extras). **Two or more become ONE "N new messages" notification ("Tap to open and check them") that opens the inbox**; a message that arrives while earlier ones are still unopened in the shade folds into that single notification and raises its count, so the shade never holds a stack of alerts. Two channels: "Important: responses and urgent help near you" (high) and "New messages on this phone" (default); a summary uses the high channel only if at least one message in it is important. Lock-screen content is generic ("New message on this phone"); the shade shows only type and area (single) or a count (summary), never the message body. Important messages announced while the app was closed also pop up inside the app, once, the moment it is opened (unless they were already opened, or the person tapped the summary, which means they are already looking at the inbox). That memory is kept in the phone's database (flags `popup` / `popped`), so it survives Android killing the process; it stays on screen for 45 s or until acted on. If system notifications are off, in-app pop-ups and the inbox still work; About shows the state and a button to turn them on. Opening a message withdraws the notifications that announced it |
| **Read / unread** | A durable per-message model in the existing `flags` table (kind `read`; `announced` for notification de-duplication), included in the snapshot. New messages are unread; opening the relevant message (not rendering a preview) marks it read; a new response to an older request, an acknowledgment of your offer, or a resolution notice for a case you answered makes that case need attention again; a renewal that only extends the time inherits the earlier version's read state, a renewal that changes the words does not. Existing messages on an upgraded phone are history (marked read, never announced). A read is local: **no packet is created, the sender is told nothing** |
| **Inbox** | Feed becomes **Inbox**: *New to you* (unread requests, updates, relevant responses) / *Active help requests* (priority: urgent, nearby, matching abilities, then recent activity) / *Community updates* / *Earlier messages* (collapsed: expired, resolved, older). Every message appears in exactly one group; each group is capped (4 / 5 / 3 / 5) with "Show N more". Filters (type, neighbourhood, abilities) are one collapsed row that states the current choice. An unread message that has expired stays in *New to you* but is labelled Expired. Cards: type, title, reported area, age or last activity, status, unread dot (and "Unread" for screen readers), and an action ("View request", "Share a sighting", "View response", "Open update"). My activity gets a **Needs your attention** section; the Inbox and My activity tabs show a badge |
| **Search** | A search icon in the Inbox opens a field. Case-insensitive, trimmed, every word must match, partial words work, results appear while typing and keyboard focus stays in the field (including across snapshot updates and refreshes). Searches title, description, category, reported area/landmark, neighbourhood, missing-person last-known place, note, community-update text and the response text this phone can show. Active **and** earlier messages. A match inside a response lists the parent request with the matching text and opens it with that response highlighted and focused. Type/area filters narrow the same search. Empty state: "No matching messages on this phone." / "Relay can only search messages that have reached this phone." No index, no network, no permission |
| **Navigation** | One function, `RelayUI.openMessage({t, caseId, packetId})`, used by cards, search results, banners, Android notifications and My activity. `reply` focuses that response; `ack` focuses the offer that was acknowledged; `broadcast` opens a new lightweight detail sheet; `resolve`/`request` open the case; an expired message opens as **Expired**; a message that is gone gets "no longer stored on this phone" and **Back to inbox** |

## Which messages interrupt? (the priority mechanism)

Decided on the phone, from the packet itself plus this phone's own declared neighbourhood. No server, no GPS, no learning.

| Message | In-app pop-up / loud channel? |
|---|---|
| A **response** (offer or possible sighting) to a request **you** made | **Important** |
| An **acknowledgment** of an offer **you** sent | **Important** |
| An **urgent** request whose reported area is your declared area **or one step away** in the neighbourhood graph | **Important** |
| A **missing-person** request whose search area (or reported area) is your declared area or one step away | **Important** |
| A request that was edited (new words) and meets the two area rules above | **Important** |
| A non-urgent request, an urgent one two or more steps away, a community update, a renewal that only extended the time, a resolution notice | not important: inbox badge + *New to you* (and a quiet system notification when the app is closed; folded into the single "N new messages" notification when several are waiting) |
| Anything on a phone with no fresh declared area | not important (the phone never guesses relevance) |

Why this shape: replies to your own request are the thing you are waiting for; nearby urgent help is what a neighbour can act on; everything else is reachable in one tap from the badge and would make the app unusable if it interrupted. The rules live in one place (`Inbox.classify`, mirrored for the browser prototype in `noticeFor`) and are unit-tested, including the negatives.

## Android plumbing

* `core/Inbox.kt`: `Ref` (validated identifiers), `Notice` (never carries body text), `ReadState`, `Inbox.classify` (what deserves attention), `NoticePlan` (batching). Pure Kotlin, unit-tested.
* `RelayEngine.onStored`: called once per packet that arrived from another phone and was newly stored. **Not** called for duplicates, rejected or expired packets, photo chunks, polling, radio-status changes, or anything this phone wrote. It runs before housekeeping (which deletes the older version of a renewed request) so a renewal can be compared with what it replaced. A failing observer cannot affect storage or forwarding.
* `NoticeCenter` (app open -> pop-up queue for important notices only; app closed -> a 3 s batching window, then `NoticePlan` (1 message = its own notification, 2+ = one summary) and `Notifier.fold` (earlier unopened notifications and new ones become one summary with a running count); important ones are remembered to pop up when the app opens; the flush timer is a single cancellable task), `ui/Notifier` (channels, unique PendingIntents, private lock-screen version, cancellation), `MainActivity` (`singleTop`, `onNewIntent`, cold-start intent, one-shot hand-over via `takePendingOpen`, an Intent is marked handled so a re-delivery cannot re-open it), `NativeBridge` (`markRead`, `takeIncoming`, `takePendingOpen`, `refreshNow`, `notificationState`, ...).
* No new permission (`POST_NOTIFICATIONS` was already declared), no internet, no Firebase, no accounts, no GPS.

## Distinct words, kept distinct

Saved on this phone / Shared with a nearby phone / Received on this phone / **Opened (read) on this phone** / Acknowledged / Resolved. A banner or notification means "this phone stored a message"; it does not mean the sender knows it was read.

## Limitations

* **Retention.** The engine evicts a received request 30 minutes after it expires (unless it involves you). "Earlier messages" shows what is still on the phone; this feature does not extend retention, because that would change storage, not just the UI.
* The notification text for a request shows type and area; the title of the request is shown in the shade for responses ("about"). Lock-screen content is generic only if the phone is set to hide sensitive notification content (the default "private" visibility honours that setting).
* Notifications come only from a running process: they exist while the radio service/app runs. If Android stops the service (battery saver), no packet is received and nothing is announced; the unread state is still there when the app opens.
* A renewal with changed words shows "New" on the card (the label "Request updated" is used by the banner/notification, which see the earlier version).
* Not tested on two physical phones: this environment has one emulator and no radio peer, so message receipt over real BLE between two handsets was not exercised. BLE forwarding code is unchanged (`ble/*`, `Link.kt`, `Policy.kt`, `Framing.kt`, `mesh.js` have no diff), but receipt-to-notification on real hardware needs the two-phone test in `docs/FIELD_TEST_CHECKLIST.md`.

## Final polish pass (`feature/mobile-inbox-final-polish`)

A focused correction pass; no new features, no change to retention, BLE forwarding or the desktop simulator.

**1. Ordering of unread messages.** *New to you* now lists still-open messages first (urgent, then close to this phone's declared area or matching its skills, then newest), then expired or resolved unread ones (same ordering among themselves). An expired unread request stays unread and findable (also by search) but ranks behind every open one even if it arrived later. Its card shows **Expired once** (the duplicate footer label is gone), has no action link, and opening it says responses are closed and offers no reply form. A message is still in exactly one group. Regression: `inbox_mixed` fixture (open urgent+close, open urgent+far, open ordinary, expired urgent, expired ordinary, resolved, expired community update) in `tests/android_ui/inbox_test.html` section 13.

**2. Sender wording.** A received response proves nothing about its sender's distance, qualification or role, so the sheet now says only what the packet carries: "From a phone that declares Green Park." (or "From another phone that has Relay." when no area was declared), followed by "What it says about the sender is not verified." A response to a missing-person report says "Possible sighting from a phone that declares ...", its button reads "Acknowledge sighting", and the card and activity timeline say "Sighting received / acknowledged" and "possible sighting", never "offer". Address-sharing copy says "sender" instead of "volunteer". Every response stays labelled Unverified.

**3. Compact area reminder.** "Still in Green Park?" with **Yes / I moved / Later** is now one row (about 56 px) at 390 px and 412 px, two rows at 360 px and below with three equal 44 px buttons, replacing a block of roughly 150 px. All three actions and the stale-area behaviour are unchanged; it still never interrupts a half-written request and is not hidden by an incoming pop-up (the pop-up sits above it). Two layout bugs found while checking 320 px were fixed in the same pass: the header logo wrapped letter by letter, and the pop-up squeezed its text into a narrow column (the pop-up now stacks its text above its buttons on narrow screens).

**4. The unexplained notification.** In the first full run, `twoNotificationsAreDistinct...` expected zero notifications after duplicate packets but found one. Investigation:

* In isolation and in later full runs, the notification list after duplicates was empty (diagnostics logged tag, id, channel, ongoing flag and foreground-service flag only), so the inbox does not re-post duplicates.
* The only legitimate non-inbox notification this app can show is the radio foreground-service notification: id `41`, no tag, channel `relay_radio`, ongoing, `FLAG_FOREGROUND_SERVICE`, title "Relay is on". Opening the app starts that service (`MainActivity.onCreate` -> `startRelay()`) once Bluetooth permissions are granted, which earlier tests in the same install had already done, and Android does not let an app cancel a foreground-service notification, so `cancelAll()` leaves it in place. A test that expects "no notifications at all" while the radio runs is therefore order-dependent.
* The exact failing run's notification was not recorded (the original assertion only reported the count), so the attribution to the radio service is the finding that fits every observation, not a captured proof of that single event. What is now proven and tested: the service notification appears when the app opens, it is distinguishable from every inbox notification (`theRadioServiceNotificationIsNotAnInboxNotification...`), and the duplicate test now asserts that **no inbox notification exists** and that **everything else showing is exactly the radio-service notification**, with full metadata in the failure message. It was not weakened to "ignore extras".
* Two other flaky failures seen on the way were real test-harness bugs and were fixed at the source: a timer left from a previous test fired into the next one (the flush is now a single cancellable task, cancelled by `resetForTest`), and "popup" flags parked by earlier tests greeted a later test (setup now clears them). Burst tests also now wait for the final count, because a slow phone may take longer than the 3 s window to store six packets and later arrivals fold into the same single notification.

**5. Regression checks** (all in the suites above): search finds active and retained earlier messages, including expired ones still stored; the empty state says only messages that reached this phone are searched; a result opens the right message; a reply-text match focuses the right response; a notification tap opens the exact message, also on cold start; read state persists across a SQLite reopen; refresh invents nothing and keeps drafts; an in-app pop-up does not repeat after a refresh; different notifications have different destinations. Retention (the engine drops a request 30 minutes after expiry unless it involves this phone) is unchanged, so search never implies that purged packets can be recovered.

**6. Notification rule requested during this pass.** One message is its own notification; two or more are one "N new messages — tap to open and check" notification (also for in-app pop-ups); loudness is a property of that single notification (loud only if something in it is important), never of every message.
